## 2026-05-23 Output scaffolding 的含义

来源：用户提供题目

题目：
> "Output scaffolding"（输出脚手架）技术是指什么？

选项：
- A. 让模型生成代码框架
- B. 在 Prompt 中提供输出的部分结构或开头，引导模型按特定格式完成
- C. 使用外部工具验证模型输出
- D. 要求模型输出多种格式

结论：
正确选项：B

大白话解析：
Output scaffolding 就是先在 Prompt 里给模型一个输出“骨架”或开头，让模型照着这个结构继续补全。它的重点不是让模型写代码框架，而是控制模型的回答格式、字段顺序和组织方式。

易错点：
- A 容易被“scaffolding”这个词误导，以为是代码脚手架；这里说的是输出结构脚手架。
- C 是输出验证，不是输出脚手架。
- D 是多格式输出要求，不是提供部分结构来引导补全。

知识点总结：
- Output scaffolding = 在 Prompt 中预先给出输出结构/开头，让模型按指定格式补全。

## 2026-05-23 评估提示词工程效果的可靠方法

来源：用户提供题目

题目：
> 以下哪个是评估提示词工程效果的最可靠方法？

选项：
- A. 只看几个主观感觉良好的示例
- B. 建立包含多样用例的评测集，通过量化指标（如准确率、格式合规率）进行系统性评估
- C. 只测试最困难的边界用例
- D. 依赖单次运行的结果判断

结论：
正确选项：B

大白话解析：
评估 Prompt 不能只凭感觉，也不能只看一两次输出。可靠做法是准备一批覆盖不同情况的测试样例，然后用明确指标衡量效果，比如答案准确率、格式合规率、拒答率、幻觉率、稳定性等。这样才能知道 Prompt 是真的变好了，还是刚好某个例子表现不错。

易错点：
- 主观感觉容易偏，几个好例子不能代表整体效果。
- 只测困难边界用例会忽略普通场景表现。
- 单次运行不可靠，模型输出有随机性。

知识点总结：
- Prompt 评估要用多样评测集 + 量化指标 + 系统性对比。

## 2026-05-23 提升 Prompt 对分布外输入鲁棒性的方法

来源：用户提供题目

题目：
> 以下哪种做法最有助于提升 Prompt 对"分布外"（Out-of-Distribution）输入的鲁棒性？

选项：
- A. 只在典型样本上测试 Prompt
- B. 在测试集中纳入边界用例和对抗样本，并在 Prompt 中加入对异常输入的处理指令（如"若输入不符合预期格式，请说明原因并请求澄清"）
- C. 增加 Temperature 参数
- D. 减少 System Prompt 的长度

结论：
正确选项：B

大白话解析：
分布外输入就是和正常输入不太一样、超出预期范围的输入，比如格式错乱、信息缺失、恶意诱导、极端边界情况。要提升鲁棒性，需要先用这些情况测试 Prompt，再在 Prompt 里写清楚异常输入怎么处理，比如说明原因、拒绝处理、请求澄清或输出固定错误格式。

易错点：
- 只测典型样本无法发现异常输入下的问题。
- 增加 Temperature 会提高随机性，通常不利于稳定处理异常输入。
- System Prompt 不是越短越好，关键是是否包含必要的边界和异常处理规则。

知识点总结：
- 提升 OOD 鲁棒性 = 测边界/对抗样本 + 明确异常输入处理策略。

## 2026-05-23 Prompt 版本控制的最佳实践

来源：用户提供题目

题目：
> 以下哪种说法正确描述了"Prompt 版本控制"的最佳实践？

选项：
- A. 只保存最新版本的 Prompt，删除历史版本
- B. 将 Prompt 存储在代码仓库中，每次修改创建新版本，记录修改原因和效果变化
- C. 将 Prompt 硬编码在业务逻辑中，避免频繁修改
- D. 只在本地保存 Prompt，不需要版本控制

结论：
正确选项：B

大白话解析：
Prompt 在实际项目里应该像代码和配置一样管理。每次改 Prompt，都应该能追踪改了什么、为什么改、效果有没有变好。如果新版本出问题，也能回滚到旧版本。

- 只保存最新版本会丢失历史记录，难以排查问题和回滚。
- 硬编码在业务逻辑里会增加维护成本，也不方便实验和版本对比。
- 只保存在本地不利于团队协作、审查和复现。

知识点总结：
- Prompt 版本控制 = 存仓库 + 记录变更原因 + 评估效果变化 + 支持回滚。

## 2026-05-23 Prompt 具体性原则

来源：用户提供题目

题目：
> 在设计 Prompt 时，"具体性"（Specificity）原则要求什么？

选项：
- A. 使用尽量多的专业术语
- B. 用精确、可量化的语言描述任务要求，避免模糊词汇
- C. 提供尽量长的背景信息
- D. 要求模型输出尽量详细的内容

结论：
正确选项：B

大白话解析：
具体性原则要求把任务说清楚，最好能量化、能检查。比如不要说“简单回答一下”，而是说“用不超过 3 句话回答”；不要说“分析得详细一点”，而是说“从成本、风险、收益三个角度各给 1 条要点”。

易错点：
- 专业术语多不等于具体，反而可能增加理解成本。
- 背景信息长不等于有效，关键是和任务相关。
- 输出详细不等于具体，具体性强调明确标准和可执行约束。

知识点总结：
- Specificity = 用明确、精确、可量化、可检查的语言描述任务和输出要求。

## 2026-05-23 Prompt Drift 的含义

来源：用户提供题目

题目：
> "Prompt 漂移"（Prompt Drift）是指什么现象？

选项：
- A. 模型在长对话中逐渐偏离最初的 System Prompt 约束
- B. Prompt 的长度随时间增加
- C. 模型输出的格式发生变化
- D. 用户不断修改 Prompt

结论：
正确选项：A

大白话解析：
Prompt Drift 指的是对话变长后，模型可能逐渐忘记或弱化最初的规则，回答开始偏离原本的角色、格式、边界或行为规范。比如一开始要求“只输出 JSON”，聊了很多轮后模型又开始输出解释文本，这可能就是漂移表现。

易错点：
- Prompt 变长不是 Prompt Drift 的定义，只可能是长对话环境中的相关因素。
- 输出格式变化可能是 Prompt Drift 的表现，但定义更广，包括角色、约束、行为边界的偏离。
- 用户修改 Prompt 是主动变更，不等于模型自己在长对话中漂移。

知识点总结：
- Prompt Drift = 长对话中模型逐渐偏离最初提示约束、角色或输出规范。

## 2026-05-23 精确率和召回率的含义

来源：用户提供题目

题目：
> 在评估 Prompt 质量时，"精确率"和"召回率"分别衡量什么？

选项：
- A. 精确率衡量速度，召回率衡量准确性
- B. 精确率衡量正确输出中有多少是真正正确的，召回率衡量所有正确案例中有多少被正确识别
- C. 精确率衡量输出长度，召回率衡量输出多样性
- D. 两者都衡量模型的推理深度

结论：
正确选项：B

大白话解析：
精确率看模型“说是对的/判为目标类的”里面，有多少真的对；召回率看所有本来应该被识别出来的正确案例里，模型找出了多少。前者关注少误报，后者关注少漏报。

易错点：
- 精确率和召回率都不是速度、输出长度、输出多样性或推理深度指标。
- 精确率高不代表召回率一定高；模型很保守时可能误报少，但漏掉很多正确案例。
- 召回率高也不代表精确率一定高；模型全都判为正可能漏报少，但误报很多。

知识点总结：
- 精确率 = 判为正的里面有多少真正；召回率 = 真正该找出的里面找出了多少。

- A/B 测试 = 一次只改一个变量，方便准确归因。

- C. 使用翻译 API 将所有内容先转换为英文

- 多语言 Prompt = 用目标语言写清任务，并明确输入语言、输出语言和是否需要翻译。

## 2026-05-23 多轮对话中的 Prompt 工程注意点

来源：用户提供题目

题目：
> 在使用多轮对话时，Prompt 工程师需要特别注意什么？

选项：
- A. 每轮都要重复整个 System Prompt
- B. 上下文窗口限制、历史对话的截断策略和角色一致性维护
- C. 每轮都要提供新的 Few-shot 示例
- D. 避免在对话中使用代词

结论：
正确选项：B

大白话解析：
多轮对话会不断积累历史内容，但模型上下文窗口有限。工程上要考虑哪些历史需要保留、哪些可以摘要或截断，以及截断后模型是否还能保持原来的角色、规则和任务状态。

易错点：
- 不需要每轮重复整个 System Prompt，但要保证核心约束持续有效。
- 每轮都给新 Few-shot 示例会增加 token 成本，也可能干扰已有上下文。
- 代词不是绝对不能用，关键是上下文是否清楚。

知识点总结：
- 多轮对话 Prompt 设计 = 管理上下文窗口、历史截断/摘要、状态追踪和角色一致性。

## 2026-05-23 Prompt Compression 技术

来源：用户提供题目

题目：
> 以下哪项正确描述了"Prompt 压缩"（Prompt Compression）技术？

选项：
- A. 将长 Prompt 缩短为一句话
- B. 使用算法或模型自动精简 Prompt 内容，在保持语义的前提下减少 token 消耗
- C. 将多个 Prompt 合并为一个
- D. 降低模型输出的精度

结论：
正确选项：B

大白话解析：
Prompt 压缩的目标是在不丢关键语义、不明显影响效果的前提下，减少 Prompt 的 token 数。它可以通过删除冗余内容、压缩上下文、保留关键信息等方式完成，常用于降低成本、减少延迟、节省上下文窗口。

易错点：
- 压缩不是强行缩成一句话；太短可能丢失关键约束。
- 合并多个 Prompt 不是压缩的定义，合并后可能更长。
- 降低输出精度不是目标，好的压缩应尽量保持效果。

知识点总结：
- Prompt Compression = 保持语义和效果的前提下，自动精简 Prompt，减少 token 消耗。

## 2026-05-23 RAG 与 Prompt 工程的结合点

来源：用户提供题目

题目：
> RAG（检索增强生成）技术与 Prompt 工程的结合点是什么？

选项：
- A. RAG 替代了 Prompt 的作用
- B. 将检索到的相关文档片段插入 Prompt 上下文，为模型提供事实依据
- C. RAG 用于优化 System Prompt
- D. RAG 减少了 Prompt 的 token 消耗

结论：
正确选项：B

大白话解析：
RAG 的核心是先从知识库、文档库或数据库里检索相关内容，再把这些内容放进 Prompt 的上下文中，让模型基于这些资料回答。它不是替代 Prompt，而是给 Prompt 增加事实依据。

易错点：
- RAG 不会替代 Prompt，仍然需要 Prompt 规定任务、格式、约束和依据使用方式。
- RAG 不是专门优化 System Prompt 的技术。
- RAG 往往会把检索片段加入上下文，token 消耗可能增加；它的主要目标是提升事实性，不是减少 token。

知识点总结：
- RAG + Prompt = 把检索到的相关文档作为上下文证据，让模型基于事实回答。

## 2026-06-11 Few-shot prompting 的核心思想

来源：用户提供题目

题目：
> Few-shot prompting 的核心思想是什么？

选项：
- A. 通过角色扮演引导模型
- B. 在提示中提供少量输入输出示例，帮助模型理解任务格式
- C. 要求模型逐步推理
- D. 限制模型的输出长度

结论：
正确选项：B

大白话解析：
Few-shot prompting 就是在 Prompt 里放几个“样例题”，让模型通过这些示例看懂任务要怎么做、输入输出格式是什么、判断标准大概是什么。它不需要改模型参数，只是靠当前上下文里的示例来引导模型。

易错点：
- A 是角色提示 Role prompting，不是 Few-shot。
- C 是 Chain-of-Thought 或分步推理提示，不是 Few-shot 的核心。
- D 是长度约束，不是示例学习。

知识点总结：
- Few-shot = 给少量输入输出示例，让模型照着格式和规律完成新任务。

## 2026-06-11 Chain-of-Verification 的步骤

来源：用户提供题目

题目：
> "Chain-of-Verification"（验证链）技术的步骤是什么？

选项：
- A. 生成答案→列出可用于验证答案的问题→独立回答每个验证问题→基于验证结果修正最终答案
- B. 多次运行推理链并投票
- C. 要求模型列出信息来源后验证
- D. 人工审核模型输出

结论：
正确选项：A

大白话解析：
Chain-of-Verification 的核心是让模型不要生成完答案就结束，而是主动检查自己的答案。流程通常是先给出初始答案，再围绕这个答案提出验证问题，然后独立回答这些验证问题，最后根据验证结果修正原答案。

易错点：
- B 更接近 Self-consistency：多次生成推理路径再投票。
- C 只强调来源验证，不是完整的验证链流程。
- D 是人工审核，不是模型自我验证流程。

知识点总结：
- Chain-of-Verification = 先答题，再提验证问题，独立验证，最后修正答案。

> "Maieutic prompting"（助产式提示）源自苏格拉底教学法，其特点是什么？

- B. 通过一系列引导性问题逐步帮助模型自己"推导"出正确答案

正确选项：B

大白话解析：
Maieutic prompting 借鉴苏格拉底式教学，不是直接把答案塞给模型，而是通过连续的引导性问题，让模型一步步检查前提、分析条件、排除错误，最后推导出更合理的答案。

## 2026-06-11 构建测试集时推荐的数据分布

来源：用户提供题目

题目：
> 构建测试集时，推荐的数据分布通常包括哪几类？

选项：
- A. 简单题、中等题、困难题
- B. 典型用例、边界用例、对抗用例、异常用例
- C. 正确答案、错误答案、模糊答案
- D. 长文本、短文本、代码文本

结论：
正确选项：B

大白话解析：
评测 Prompt 不能只看正常情况，还要看各种容易出问题的情况。典型用例测试日常表现，边界用例测试临界条件，对抗用例测试是否容易被诱导或绕过规则，异常用例测试输入缺失、格式错误、不符合预期时是否能稳定处理。

- A 的难度分层有价值，但不如 B 覆盖 Prompt 工程中的真实风险类型。
- C 更像答案类型，不是完整的测试用例分布设计。
- D 是输入形态分类，不足以覆盖边界、攻击和异常情况。

知识点总结：
- Prompt 测试集 = 典型用例 + 边界用例 + 对抗用例 + 异常用例。

## 2026-06-11 Zero-shot prompting 的定义

来源：用户提供题目

题目：
> 以下哪种提示方式不向模型提供任何示例，直接要求模型完成任务？

选项：
- A. Few-shot prompting
- B. Zero-shot prompting
- C. Chain-of-Thought prompting
- D. Role prompting

结论：
正确选项：B

大白话解析：
Zero-shot prompting 就是不提供输入输出示例，直接告诉模型任务，让模型凭已有能力完成。比如只写“请判断下面评论的情感倾向”，但不给任何示例，这就是 Zero-shot。

易错点：
- Few-shot 会提供少量示例。
- Chain-of-Thought 强调逐步推理，不等于不给示例；它可以是 zero-shot CoT，也可以配合示例。
- Role prompting 强调设定角色，比如“你是客服专家”，不是示例数量的分类。

知识点总结：
- Zero-shot = 不给示例，直接下任务。

## 2026-06-11 提高模型在专业领域表现的 Prompt 做法

来源：用户提供题目

题目：
> 以下哪种做法最有助于提高模型在专业领域的表现？

选项：
- A. 仅依赖模型的预训练知识
- B. 结合领域专业术语、专业示例和明确的领域约束进行 Prompt 设计
- C. 使用最短的 Prompt
- D. 避免在 Prompt 中使用专业词汇

结论：
正确选项：B

大白话解析：
专业领域任务通常有专门术语、判断标准、行业规范和边界条件。Prompt 里要把这些领域信息讲清楚，最好给专业示例和明确约束，让模型按该领域的规则回答，而不是只靠泛泛的常识。

易错点：
- 只依赖预训练知识，容易过时、泛化或不符合具体业务标准。
- Prompt 不是越短越好，关键是必要信息要完整。
- 专业词汇不能一概避免；在专业任务里，正确使用术语反而能减少歧义。

知识点总结：
- 专业领域 Prompt = 领域术语 + 专业示例 + 明确约束 + 必要背景。

## 2026-06-11 Question-first 策略的好处

来源：用户提供题目

题目：
> 在 Prompt 中使用"先提问再回答"（Question-first）策略的好处是什么？

选项：
- A. 减少模型的推理时间
- B. 让模型在生成答案之前先明确问题的核心，避免答非所问
- C. 提高模型的创意输出
- D. 减少 Prompt 的 token 消耗

结论：
正确选项：B

大白话解析：
Question-first 策略就是让模型先把问题核心弄清楚，再开始回答。这样可以减少模型还没理解清楚就直接输出的情况，尤其适合问题复杂、条件多、容易误解的任务。

易错点：
- 它不一定减少推理时间，反而可能多一步澄清或分析。
- 它不是为了提高创意输出。
- 先提问或先明确问题通常会增加一些 token，不是为了减少 token 消耗。

知识点总结：
- Question-first = 先明确问题核心，再回答，避免答非所问。

## 2026-06-11 避免模型输出有偏见内容的提示方式

来源：用户提供题目

题目：
> 以下哪种方式最能有效引导模型避免输出有偏见的内容？

选项：
- A. 完全不提及偏见话题
- B. 在 System Prompt 中明确要求公平、平衡地对待不同群体，并在敏感话题上要求呈现多方观点
- C. 使用更高的 Temperature 增加多样性
- D. 减少 Prompt 中的示例数量

结论：
正确选项：B

大白话解析：
要减少偏见，不能靠回避话题，而要在系统层明确行为规范。比如要求模型公平对待不同群体、不使用刻板印象、不把个体问题泛化到群体，并且在敏感话题上尽量平衡呈现多方观点。

易错点：
- A 回避偏见话题不等于解决偏见；模型遇到相关问题时仍可能处理不好。
- C 提高 Temperature 只会增加随机性，不会自动变公平。
- D 减少示例数量不能直接减少偏见；如果示例本身有偏，反而要校准示例质量。

知识点总结：
- 避免偏见 = 在 System Prompt 中明确公平、平衡、反刻板印象和敏感话题处理规则。

## 2026-06-11 Decomposed prompting 与 Prompt chaining 的关系

来源：用户提供题目

题目：
> "Decomposed prompting"（分解式提示）与"Prompt chaining"的关系是什么？

选项：
- A. 两者完全相同
- B. 分解式提示是一种 Prompt chaining 的设计方法，强调通过专用子提示处理不同子任务
- C. 分解式提示不使用多次 API 调用
- D. Prompt chaining 不需要分解任务

结论：
正确选项：B

大白话解析：
分解式提示就是把一个复杂任务拆成多个更小的子任务，每个子任务用专门的 Prompt 处理。Prompt chaining 则是把这些步骤串起来，让前一步的输出成为后一步的输入。因此，分解式提示可以看作 Prompt chaining 的一种设计方式。

易错点：
- 两者关系很近，但不完全等同。分解式提示强调“拆任务”，Prompt chaining 强调“步骤串联”。
- 分解式提示在工程实现中经常会涉及多次调用，也可能在一次 Prompt 内模拟多个步骤，不能说它一定不使用多次 API 调用。
- Prompt chaining 通常就是为了把复杂任务拆成多个步骤处理。

知识点总结：
- Decomposed prompting = 拆子任务；Prompt chaining = 把子任务步骤串起来执行。

## 2026-06-11 Multi-Agent 系统中 Agent Prompt 的设计原则

来源：用户提供题目

题目：
> 在多智能体（Multi-Agent）系统中，每个 Agent 的 Prompt 设计应遵循什么原则？

选项：
- A. 所有 Agent 共用同一个 System Prompt，保持一致性
- B. 每个 Agent 有明确的职责边界，Prompt 定义其专属能力、输入来源和输出格式
- C. Agent 的 Prompt 越长越好，覆盖所有可能情况
- D. Agent 之间不需要约定交互格式

结论：
正确选项：B

大白话解析：
多智能体系统里，每个 Agent 应该像团队里的不同岗位一样，各自负责清楚的任务。Prompt 需要定义它负责什么、不负责什么、能使用哪些输入、产出什么格式，以及如何和其他 Agent 交接结果。这样才能减少职责重叠、重复工作和输出混乱。

易错点：
- 所有 Agent 共用同一个 System Prompt 会导致分工不清，不适合多角色协作。
- Prompt 不是越长越好，关键是职责、边界和接口清晰。
- Agent 之间必须约定交互格式，否则前一个 Agent 的输出可能无法被后一个 Agent 稳定使用。

知识点总结：
- Multi-Agent Prompt = 明确每个 Agent 的职责边界、专属能力、输入来源、输出格式和协作接口。

## 2026-06-11 Function Calling 的主要作用

来源：用户提供题目

题目：
> Function Calling（函数调用）在 LLM 中的主要作用是什么？

选项：
- A. 让模型自动编写函数代码
- B. 让模型以结构化方式输出参数，触发外部函数或 API 调用
- C. 提高模型的数学计算能力
- D. 让模型记忆历史对话

结论：
正确选项：B

大白话解析：
Function Calling 的作用是让模型判断什么时候需要调用外部函数，并按函数要求生成结构化参数。真正执行函数或 API 的通常是外部系统，不是模型自己直接执行。

易错点：
- Function Calling 不是让模型自动写函数代码，而是调用已经定义好的函数或工具。
- 它可以借助计算器等工具间接提升计算可靠性，但本身不是提高模型数学能力。
- 历史对话记忆属于上下文管理或记忆系统，不是 Function Calling 的主要作用。

知识点总结：
- Function Calling = 模型生成结构化调用参数，由外部系统执行函数/API。
