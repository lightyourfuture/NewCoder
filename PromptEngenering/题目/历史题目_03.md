## 2026-06-11 同一 Prompt 在不同模型上效果差异的原因

来源：用户提供题目

题目：
> 以下哪个因素会导致同一 Prompt 在不同模型上效果差异显著？

选项：
- A. 服务器地理位置
- B. 不同模型的预训练数据、RLHF 偏好和指令遵循能力存在差异
- C. 请求的时间段
- D. 用户账号的订阅等级

结论：
正确选项：B

大白话解析：
不同模型不是“同一个脑子”。它们训练用的数据、模型结构、对齐方式、RLHF 偏好、安全策略、指令遵循能力都可能不同。所以同一个 Prompt，在一个模型上表现稳定，在另一个模型上可能格式乱、理解偏、拒答多或回答风格不同。

易错点：
- 服务器地理位置通常不是 Prompt 效果差异的核心原因。
- 请求时间段一般不会决定模型理解能力。
- 用户订阅等级可能影响能用哪个模型或额度，但不是同一 Prompt 在不同模型上表现差异的本质原因。

知识点总结：
- Prompt 效果会受模型差异影响：预训练数据、对齐偏好、能力边界和指令遵循能力都不同。

## 2026-06-11 Knowledge Cutoff 对 Prompt 工程的影响

来源：用户提供题目

题目：
> 以下哪种说法正确描述了 LLM 的"知识截止日期"（Knowledge Cutoff）对 Prompt 工程的影响？

选项：
- A. 知识截止日期后的信息模型完全无法处理
- B. 对于知识截止日期之后的信息，需要通过 RAG、搜索工具或在 Prompt 中直接提供最新信息来补充
- C. 只需切换到更新的模型版本即可解决
- D. 通过增加 Temperature 可以让模型"猜测"最新信息

结论：
正确选项：B

大白话解析：
知识截止日期表示模型训练知识大致停留在某个时间点。这个时间点之后的新政策、新产品、新价格、新论文、新事件，模型不一定知道，或者知道得不可靠。Prompt 工程上要把最新信息补给模型，比如通过 RAG 检索资料、联网搜索工具，或者直接把最新文档贴进 Prompt。

易错点：
- A 说“完全无法处理”太绝对。模型可以处理你提供的新信息，但不能凭空可靠知道新信息。
- C 不够可靠。更新模型可能知识更新一些，但仍然会有新的截止日期，也不能保证覆盖你的具体业务资料。
- D 错。Temperature 只控制随机性，不能让模型可靠获得最新事实；让模型猜最新信息会增加幻觉风险。

知识点总结：
- Knowledge Cutoff 之后的信息，要靠 RAG、搜索工具或 Prompt 中提供资料来补充；不要让模型猜。

## 2026-06-11 提升模型对长文档理解能力的方法

来源：用户提供题目

题目：
> 以下哪种方式最能有效提升模型对长文档的理解能力？

选项：
- A. 直接将整个文档放入 Prompt
- B. 使用分段摘要、Map-Reduce 或滑动窗口技术处理超长文档
- C. 要求模型忽略文档细节
- D. 增加 Few-shot 示例

结论：
正确选项：B

大白话解析：
长文档通常信息多、结构复杂，甚至可能超过上下文窗口。更稳的做法是把文档切成片段，分别摘要或提取要点，再汇总；或者用滑动窗口保留相邻片段上下文；也可以用 Map-Reduce 先分块处理，再统一合并结果。

易错点：
- 直接塞整篇文档可能超出上下文窗口，也可能导致模型忽略中间细节。
- 要求忽略细节会降低理解质量，不适合需要准确分析的任务。
- Few-shot 示例可以说明任务格式，但不能根本解决长文档上下文过长和信息组织问题。

知识点总结：
- 长文档处理 = 分段处理 + 摘要/提取 + Map-Reduce 汇总 + 滑动窗口保留上下文。

- Calibration = 让模型输出的置信度和实际准确率尽量匹配。

## 2026-06-11 Prompt 工程与 Fine-tuning 的选择原则

来源：用户提供题目

题目：
> 以下哪项正确描述了"Prompt 工程"与"Fine-tuning"的选择原则？

选项：
- A. Fine-tuning 总是优于 Prompt 工程
- B. 当任务可以通过清晰的指令和示例完成时先用 Prompt 工程；当需要大量特定风格/知识/格式的适配时再考虑 Fine-tuning
- C. Prompt 工程只适合简单任务
- D. Fine-tuning 不需要数据，成本更低

结论：
正确选项：B

大白话解析：
Prompt 工程通常成本低、迭代快，适合先验证任务能不能通过清晰指令、约束、示例和上下文解决。如果任务需要模型长期稳定地适配某种专业风格、固定格式、业务规则或大量领域样例，仅靠 Prompt 很难稳定时，再考虑 Fine-tuning。

易错点：
- Fine-tuning 不是总是更好，它需要数据、训练成本和评估流程。
- Prompt 工程不只适合简单任务，复杂任务也可以通过分解、RAG、工具调用、Prompt chaining 等方式解决。
- Fine-tuning 通常需要高质量训练数据，不是无数据、低成本方案。

知识点总结：
- 选择原则：先 Prompt 工程快速验证和迭代；Prompt 难以稳定适配大量特定模式时，再考虑 Fine-tuning。

## 2026-06-11 创意头脑风暴的 Prompt 设计

来源：用户提供题目

题目：
> 以下哪种 Prompt 设计最适合让模型给出有创意的头脑风暴建议？

选项：
- A. "请给出10个关于X的想法"
- B. "请用发散思维列出20个关于X的创意，包括常规想法和非常规想法，不要自我审查，先数量后质量"
- C. "请给出关于X最好的方案"
- D. "请严格按照逻辑给出X的解决方案"

结论：
正确选项：B

大白话解析：
头脑风暴的目标是先打开思路，而不是一开始就筛出唯一最优方案。B 明确要求发散思维、数量更多、包含常规和非常规想法，并且先数量后质量，这些都能鼓励模型输出更多样、更有创意的结果。

易错点：
- A 太普通，只要求数量，没有明确创意方向和发散要求。
- C 会让模型过早收敛到一个“最好方案”，不适合头脑风暴阶段。
- D 强调严格逻辑和解决方案，更适合分析或决策，不适合发散创意。

知识点总结：
- 创意头脑风暴 Prompt = 发散思维 + 多数量 + 常规/非常规都要 + 先数量后质量。

## 2026-06-11 Least-to-most prompting 的思路

来源：用户提供题目

题目：
> "Least-to-most prompting"（由简到繁提示）技术的思路是什么？

选项：
- A. 先给模型最简单的任务，再逐渐增加难度
- B. 将复杂问题分解，先解决最简单的子问题，再将子问题的解用于解决更复杂的子问题
- C. 从最少的 token 开始，逐渐增加 Prompt 长度
- D. 先给出最少的约束，再逐渐收紧

结论：
正确选项：B

大白话解析：
Least-to-most prompting 是把一个复杂问题拆成一串子问题，先解决最基础、最简单的部分，再把前面得到的结果作为后面更复杂步骤的依据。它强调“子问题之间有依赖关系”，不是简单地随机从易到难做题。

易错点：
- A 只说“逐渐增加难度”，不够准确；关键是前面子问题的答案要服务后面子问题。
- C 是 token 长度控制，不是 Least-to-most。
- D 是约束逐渐收紧，不是由简到繁推理。

知识点总结：
- Least-to-most prompting = 复杂问题拆成依赖子问题，先解简单部分，再逐步解决复杂部分。

## 2026-06-11 Token Budget 管理

来源：用户提供题目

题目：
> 以下哪种说法正确描述了"Token 预算"（Token Budget）管理？

选项：
- A. 只需限制输出的最大 token 数
- B. 合理分配输入中各部分的 token 占比（System Prompt、Few-shot 示例、检索内容、用户输入），确保关键内容不被截断
- C. Token 预算只影响成本，不影响质量
- D. 上下文越长模型效果越好，无需管理 token 预算

结论：
正确选项：B

大白话解析：
Token 预算管理就是安排有限的上下文空间该给谁用。System Prompt、Few-shot 示例、RAG 检索内容、用户输入和模型输出都要占 token。如果不管理，关键规则、重要证据或用户问题可能被截断，导致模型答错、格式乱或遗漏信息。

- 只限制输出长度不够，输入上下文也需要预算管理。

- 上下文不是越长越好；太长可能引入噪声，也会挤占关键内容空间。

知识点总结：
- Token Budget = 合理分配 System Prompt、示例、检索内容、用户输入和输出空间，避免关键内容被截断。

- D 更接近反复迭代，不是提示链的核心定义。

- Prompt chaining = 拆子任务 + 前一步输出作为后一步输入。

- B. 模型在单次推理中能处理的最大 token 数量（包含输入和输出）

正确选项：B

大白话解析：
上下文窗口就是模型一次回答时最多能“看见”和“生成”的 token 总量。这里面包括 System Prompt、历史对话、用户输入、检索资料、示例，以及模型本次要输出的内容。

易错点：
- A 不准确。历史对话轮数不是固定标准，关键是这些历史内容占了多少 token。
- C 是训练数据规模，不是上下文窗口。
- D 是并发能力，不是模型单次处理文本的容量。

知识点总结：
- Context Window = 单次推理可处理的最大 token 容量，包含输入和输出。

## 2026-06-11 不修改模型参数执行专业任务的技术

来源：用户提供题目

题目：
> 以下哪种技术用于在不修改模型参数的情况下，让模型执行特定领域的专业任务？

选项：
- A. 预训练（Pre-training）
- B. 监督微调（Supervised Fine-tuning）
- C. 提示工程（Prompt Engineering）
- D. 知识蒸馏（Knowledge Distillation）

结论：
正确选项：C

大白话解析：
提示工程不改变模型本身，而是通过设计输入提示，把任务目标、领域背景、专业术语、示例、约束和输出格式告诉模型，让模型在当前上下文中完成专业任务。

易错点：
- 预训练会训练模型参数。
- 监督微调会用标注数据继续训练模型参数。
- 知识蒸馏通常是让小模型学习大模型，也涉及训练过程。

知识点总结：
- Prompt Engineering = 不改模型参数，通过提示词引导模型完成任务。

## 2026-06-11 Prompt 四要素中最不可缺少的部分

来源：用户提供题目

题目：
> Prompt 中的"指令"、"上下文"、"输入"、"输出格式"四要素中，最不可缺少的是哪个？

选项：
- A. 上下文
- B. 指令
- C. 输入
- D. 输出格式

结论：
正确选项：B

大白话解析：
指令是告诉模型“要做什么”的部分。没有指令，模型即使拿到了上下文和输入，也不知道是要总结、翻译、分类、改写还是提取信息。上下文、输入、输出格式都能提高效果和稳定性，但最基础、最不可缺少的是任务指令。

易错点：
- 上下文能补充背景，但不是所有任务都必须有额外上下文。
- 输入很重要，但有些任务可以直接基于指令生成内容。
- 输出格式能提高可控性，但没有格式要求时模型也能回答；没有指令则任务目标不明确。

知识点总结：
- Prompt 最核心的是指令：先说明模型要完成什么任务。

## 2026-06-11 Zero-shot CoT 的适用场景

来源：用户提供题目

题目：
> 以下哪种情况最适合使用 Zero-shot CoT？

选项：
- A. 简单的文本分类任务
- B. 需要多步推理的数学或逻辑问题，且缺乏足够的标注示例
- C. 需要快速生成大量文本
- D. 需要模型保持简洁的对话场景

结论：
正确选项：B

大白话解析：
Zero-shot CoT 就是在没有示例的情况下，用类似“让我们一步一步思考”的提示，引导模型展开中间推理。它适合数学题、逻辑题、复杂判断题这类需要多步推理的任务，尤其是在没有足够 Few-shot 示例时。

易错点：
- 简单文本分类通常不需要 CoT，直接 Zero-shot 或 Few-shot 就够了。
- CoT 会增加推理步骤和输出长度，不适合追求快速大量生成。
- 如果要求对话简洁，CoT 可能反而太啰嗦。

知识点总结：
- Zero-shot CoT = 没有示例时，引导模型一步步推理，适合多步数学/逻辑问题。

## 2026-06-12 System Prompt 中定义模型身份的目的

来源：用户提供题目

题目：
> 在 System Prompt 中定义模型身份的主要目的是什么？

选项：
- A. 增加输出的 token 数量
- B. 约束模型的行为边界、语气和能力范围
- C. 提高模型的推理速度
- D. 减少模型的幻觉

结论：
正确选项：B

大白话解析：
在 System Prompt 中定义模型身份，是为了让模型知道自己应该以什么角色、什么语气、什么能力边界来回答。比如定义为“严谨的法律助手”，模型就应该更关注法律风险、谨慎表达、不越权给最终法律裁决。

易错点：
- 定义身份不是为了增加输出 token。
- 它不会直接提高推理速度。
- 清晰的身份和边界可能间接减少胡乱回答，但“减少幻觉”不是定义身份的主要目的；减少幻觉更常用的是引用依据、RAG、要求不确定时说明不知道等策略。

知识点总结：
- System Prompt 身份定义 = 约束角色、行为边界、语气和能力范围。

## 2026-06-12 Hallucination 的含义

来源：用户提供题目

题目：
> "Hallucination"（幻觉）在 LLM 中是指什么现象？

选项：
- A. 模型输出速度过慢
- B. 模型生成看似合理但实际上错误或捏造的信息
- C. 模型拒绝回答问题
- D. 模型输出格式不正确

结论：
正确选项：B

大白话解析：
幻觉就是模型一本正经地说错话。它生成的内容可能语气很确定、逻辑看起来也顺，但事实是错的，或者资料中根本没有这个信息，是模型编出来的。

易错点：
- 输出慢是性能问题，不是幻觉。
- 拒绝回答可能是安全策略或信息不足，不等于幻觉。
- 输出格式不正确是格式遵循问题，不是事实捏造。

知识点总结：
- Hallucination = 模型生成看似合理但实际错误、无依据或捏造的信息。

## 2026-06-12 Semantic similarity 的应用场景

来源：用户提供题目

题目：
> "Semantic similarity"（语义相似度）在 Prompt 工程中的应用场景是什么？

选项：
- A. 衡量 Prompt 的长度是否合适
- B. 在 RAG 中检索与用户问题语义最相关的文档片段，或在评估中比较模型输出与参考答案的语义接近程度
- C. 检测 Prompt 中的语法错误
- D. 测量模型输出的语言复杂度

结论：
正确选项：B

大白话解析：
语义相似度看的是两段文本“意思像不像”，不是字面上完全一样。它可以用于 RAG：把用户问题和文档片段转成向量，找语义最接近的资料；也可以用于评估：比较模型答案和标准答案表达的意思是否接近。

易错点：
- 语义相似度不衡量 Prompt 长度。
- 语法错误检测关注语言形式，不是语义接近程度。
- 语言复杂度看词汇、句子、可读性等，不是语义相似度的核心用途。

知识点总结：
- Semantic similarity = 衡量文本意思是否接近，常用于 RAG 检索和答案评估。

## 2026-06-12 Lost in the Middle 问题

来源：用户提供题目

题目：
> "Lost in the Middle"（中间遗忘）问题是指什么？

选项：
- A. 模型在长对话中忘记早期消息
- B. 当相关信息位于长文档的中间部分时，模型表现比信息在开头或结尾时更差
- C. 模型在 Prompt 中间位置的指令遵循率下降
- D. 多轮对话中模型偏离主题

结论：
正确选项：B

大白话解析：
Lost in the Middle 指的是长上下文里，模型对开头和结尾的信息更敏感，而对中间位置的信息更容易忽略。因此，如果关键证据被放在长文档中间，模型可能没有很好利用，表现会比关键证据在开头或结尾时更差。

易错点：
- A 更像长对话记忆或上下文截断问题，不是 Lost in the Middle 的精确定义。
- C 接近但不准确；核心不是“中间位置的指令”，而是相关信息/证据位于长上下文中间时更难被利用。
- D 是话题漂移，不是中间遗忘。

知识点总结：
- Lost in the Middle = 长上下文中，位于中间的关键信息更容易被模型忽略。

## 2026-06-12 Analogical prompting 的核心思想

来源：用户提供题目

题目：
> "Analogical prompting"（类比提示）技术的核心思想是什么？

选项：
- A. 用类比解释复杂概念
- B. 让模型先自行回忆并生成与当前问题相关的类似例子，再利用这些例子辅助解题
- C. 要求模型用比喻输出答案
- D. 提供来自其他领域的类比示例作为 Few-shot

结论：
正确选项：B

大白话解析：
Analogical prompting 的重点是让模型先想出和当前问题相似的例子，借助这些类似例子的解法、结构或规律，再来解决当前问题。它更像“先找相似题，再参考相似题的思路解这道题”。

易错点：
- A 是用类比做解释，不是类比提示的完整技术流程。
- C 是要求输出风格像比喻，不是用类似案例辅助推理。
- D 接近 Few-shot，但 Analogical prompting 的关键是模型自己生成相关类似例子，而不是用户直接给固定示例。

知识点总结：
- Analogical prompting = 先生成相似案例，再利用相似案例的规律辅助解决当前问题。

## 2026-06-12 Prompt 工程与 In-Context Learning 的关系

- A. 两者完全独立，没有关联
- B. Prompt 工程是设计和优化 Prompt 的实践，而 In-Context Learning 是 LLM 能够从 Prompt 中学习的底层能力，前者利用后者
- C. In-Context Learning 是 Prompt 工程的子集
- D. 上下文学习要求更新模型参数

大白话解析：
Prompt 工程是人设计提示词的实践，比如写清任务、放示例、加约束、规定格式。In-Context Learning 是模型看到 Prompt 里的说明和示例后，在不改参数的情况下临时学会当前任务的能力。Prompt 工程能起作用，很大程度上就是利用了模型的上下文学习能力。

- 两者不是独立的，Prompt 工程经常利用上下文学习。
- In-Context Learning 不是 Prompt 工程的子集，它更像模型具备的一种能力。
- 上下文学习不更新模型参数，微调才会更新参数。

知识点总结：
- Prompt 工程 = 设计提示词的实践；In-Context Learning = 模型从上下文中临时学习任务的能力。

- C. 让模型总结一篇文章
- D. 让模型回答开放性问题

正确选项：B

大白话解析：
约束生成就是限制模型只能按指定范围或格式输出。最典型的场景是分类任务：输出必须是固定标签之一，比如“财经/体育/科技/娱乐”，不能自由发挥出其他标签。

- 摘要任务可以要求长度和格式，但不一定必须使用严格的约束生成。
- 固定标签分类对输出合法性要求最高，最适合约束生成。

知识点总结：
- Constrained generation = 限制模型只能输出指定格式或指定候选集合，常用于固定标签分类。

## 2026-06-12 Prompt Overfitting 现象

来源：用户提供题目

题目：
> 以下哪个正确描述了"Prompt 过拟合"（Prompt Overfitting）现象？

选项：
- A. Prompt 太长导致模型超出上下文窗口
- B. Prompt 在测试集上表现很好，但泛化到真实用户场景时效果大幅下降
- C. 模型对 Prompt 中的关键词过度敏感
- D. Prompt 使用了太多专业术语

结论：
正确选项：B

大白话解析：
Prompt 过拟合就是把 Prompt 调得太贴合某一批测试样例了，导致它在这批样例上表现很好，但遇到真实用户的不同表达、边界情况或新场景时效果明显下降。它和机器学习里的过拟合很像：对测试样例“背熟了”，但泛化能力差。

易错点：
- A 是上下文窗口或 token 预算问题，不是过拟合。
- C 可能是 Prompt 脆弱性或关键词敏感问题，但不是 Prompt 过拟合的标准定义。
- D 是表达方式问题，专业术语太多可能影响理解，但不等于过拟合。

知识点总结：
- Prompt Overfitting = 对固定测试集调得太好，但到真实场景泛化变差。
